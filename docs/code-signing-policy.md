# Code signing policy

MatterHelm is an [MIT-licensed](../LICENSE), fully open-source project with no
proprietary components. The project is applying to the SignPath Foundation
open-source code-signing programme under the
[SignPath terms](https://signpath.org/terms).

> **Applies after approval:** Free code signing provided by SignPath.io, certificate by SignPath Foundation

Until SignPath approves the application and signing is integrated into the
release workflow, MatterHelm releases are **unsigned**. Users can still verify
release integrity and build provenance with `SHA256SUMS.txt` and GitHub's
cryptographically signed attestations, as described below. When signing is
enabled, Windows will show **SignPath Foundation** as the publisher; the
certificate will not identify the MatterHelm maintainer as the publisher.

## Signing scope

After approval, each release signing request will cover the executable code
that Windows runs or installs:

- `MatterHelm.exe`, the tray application;
- `sidecar/bridge.exe`, the bundled Matter bridge;
- `MatterHelm-Setup-<version>.exe`, the installer; and
- the uninstaller generated by Inno Setup during installation.

The portable `.zip`, `SHA256SUMS.txt`, source archives, documentation, license,
notices, and non-executable configuration or manifest files are not
Authenticode-signed. The release checksum manifest and GitHub attestations
cover the downloadable packages, including the portable archive, while the
signed executables inside those packages provide the Windows publisher
identity. Signing does not replace the existing checksum and provenance
checks.

## Verifiable release path

Official releases are built only by the public, tag-triggered
[`release.yml`](../.github/workflows/release.yml) workflow. A pushed `v*` tag
checks out that public source revision, verifies that the tag matches both
package versions, and runs the bridge verification, Release app build, and app
tests before packaging. The workflow then:

- uses the exact Node.js version in [`.node-version`](../.node-version) and the
  .NET SDK selected by [`global.json`](../global.json);
- verifies the downloaded `node.exe` against Node.js's published SHA-256
  manifest through [`build.ps1`](../build.ps1);
- identifies every GitHub Action by a full commit SHA;
- creates the portable archive and Inno Setup installer from the public
  repository sources;
- publishes `SHA256SUMS.txt` and SLSA build-provenance attestations for both
  packages and the checksum manifest; and
- uploads a draft release, verifies its complete asset set, and only then
  publishes it; GitHub's immutable-release setting then prevents published
  assets or tags from being replaced.

The signing step will submit only artifacts produced by this workflow. It will
not accept locally built or substituted binaries.

## Roles and release approval

- **Author — committers.** Authors propose source or workflow changes. Every
  change lands through a pull request and must pass the repository's required
  CI checks.
- **Reviewer — independent AI reviewer.** MatterHelm is solo-maintained, so it
  does not claim a second human reviewer. Each change receives an independent
  review by a separate AI reviewer under the documented maker-not-equal-to-
  checker process in [`CLAUDE.md`](../CLAUDE.md) and the adversarial-review
  rules in [`CONTRIBUTING.md`](../CONTRIBUTING.md#one-story-per-pr-adversarial-review).
- **Approver — maintainer.** The maintainer reviews the completed release
  evidence and manually approves every SignPath release-signing request. No
  release signing request is auto-approved.

All people who can access the GitHub project or its SignPath project must
enable multi-factor authentication on the corresponding GitHub and SignPath
accounts. Access must be limited to the role needed and removed when it is no
longer needed.

## Privacy

**This program will not transfer any information to other networked systems unless specifically requested by the user or the person installing or operating it.**

In concrete terms, MatterHelm sends no telemetry and has no MatterHelm cloud
service. Its normal device traffic is confined to the local Matter fabric, and
its authenticated tray-to-sidecar IPC is confined to loopback. The only
separate outbound feature is an optional update check against GitHub Releases:
a manual check is user-requested, and a background check can be disabled;
MatterHelm asks for consent before downloading an update. Diagnostics exports
are saved locally and are never uploaded automatically. See the [user-guide
privacy notes](user-guide.md#privacy-notes) for operational detail.

## Verifying a release

Download the chosen release asset and `SHA256SUMS.txt` from the same GitHub
release. Replace `vX.Y.Z` and the example filename below with that release's
actual values.

GitHub CLI can verify that an asset belongs to the release and verify its SLSA
provenance attestation:

```text
gh release verify-asset vX.Y.Z ./MatterHelm-Setup-X.Y.Z.exe --repo fdymond/matterhelm
gh attestation verify ./MatterHelm-Setup-X.Y.Z.exe --repo fdymond/matterhelm
```

Verify the checksum on Windows PowerShell:

```powershell
$asset = "MatterHelm-Setup-X.Y.Z.exe"
$expected = ((Select-String -Path .\SHA256SUMS.txt -Pattern "  $([regex]::Escape($asset))$").Line -split '\s+')[0]
$actual = (Get-FileHash -Path ".\$asset" -Algorithm SHA256).Hash.ToLowerInvariant()
if ($actual -cne $expected) { throw "SHA-256 mismatch" }
"SHA-256 verified: $actual"
```

Verify it on Linux:

```bash
grep '  MatterHelm-Setup-X.Y.Z.exe$' SHA256SUMS.txt | sha256sum --check -
```

Verify it on macOS:

```bash
grep '  MatterHelm-Setup-X.Y.Z.exe$' SHA256SUMS.txt | shasum --algorithm 256 --check
```

After SignPath signing is enabled, the Windows file properties and
Authenticode tools should report `SignPath Foundation` as the publisher. A
publisher mismatch, invalid signature, checksum mismatch, or failed
attestation must be treated as a failed verification; do not run the file.

## Reporting a problem

Report a suspected signing compromise, unexpected publisher, verification
failure, or other security issue privately by following
[`SECURITY.md`](../SECURITY.md). Do not disclose a suspected vulnerability in a
public issue before it has been triaged.
